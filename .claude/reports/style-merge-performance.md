# 层层合并的样式：运行时引擎与原生 CSS 的性能对比（2026-11-06）

快照：master @ 417081a5，Windows 11、Node 24、Vue 3.5.44、Vite 8.3.4、Playwright 1.64.1 自带的 Chromium（无头）。
本机后台有别的负载，单轮波动 ±30–40%：结论只取多轮中位数里方向稳定、幅度远大于波动的差距。
基准进了仓库：页面 `apps/docs/bench/style-merge.tsx`，脚本 `scripts/docs/style-merge.mjs`（用法见脚本开头）。

## 1. 结论

1. **样式引擎本身不慢，不必为性能换成原生 CSS。** 同样的声明、同样的层叠顺序，引擎的样式路径与"原生 CSS + `@layer` + Vue 类数组"
   在重渲染、挂载、换档位、换主题上持平（差别在波动之内），换档位还略快（一个元素只匹配一个类）。
   动态值、有限状态的绑定不重新渲染组件，比原生写法快 25–43%（STYLE-ENGINE.md §9 已测）。
2. **差距在两处，都不是"合并"这件事本身：**
   - **新组合类的创建**：每个约 0.17 ms（插入规则 36%、查属性优先级 24%、排序 15%、合并 / 序列化 / 哈希其余）。
     一个页面 100–300 个，一次性 20–50 ms；风险在于**定制层与使用方覆盖叠加时组合数相乘**：
     基准里 1300 个组合类多花 217 ms，样式表涨到 1.95 MB / 4239 条规则（原生 10 KB / 134 条）。
   - **组件库这一层**（真实的 Button 比只走引擎的写法）：重渲染多 50%，冷挂载的脚本时间 3 倍，内存 2.4 倍。
     剖析里最大的一块是部件属性合并（`mergeProps` 对 `...rest` 的 Proxy 判空、展开、逐键合并），约 13 µs / 按钮 / 次渲染，
     样式引擎自身每次渲染不到 2 µs。
3. **低风险的原型已经做了（工作树 `exp/style-merge-opt`），见 §5**：查优先级记忆化、排序前算好权重；`mergeProps` 不再穿过
   `...rest` 的 Proxy（tsx 新增 `ownProps` 交出背后的普通对象）；配方按实例记住上一次的档位。
   剖析里 Button 每次渲染的属性合并 −78%（约 12 µs / 按钮），新组合类的 JS 部分 −38%；
   墙钟时间上 Button 各场景的脚本时间 −19% ~ −37%（重渲染 85 → 56 ms / 2000 个），JS 堆 −13%。
4. **建议**（§8）：先合入原型；组件库层继续压每次渲染的分配；定制层"不相乘"是结构性改动，要拍板；整体换原生 CSS 或原子类不做。

## 2. 怎么测的

2000 个按钮，6 样式 × 6 色调 × 3 字号 = 108 种组合轮流取；生产构建；每轮每种写法新开一页（冷挂载才可比），写法之间交错，
每个场景前先 GC；7 轮取中位数。`script` = 改状态到 Vue 更新完（渲染、比对、改 DOM、插规则），`layout` = 之后强制布局（样式重算 + 布局）。

| 写法     | 是什么                                                                                                                         |
| -------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `real`   | 组件库的 Button：`useDefaults` + `useRecipe` + `buttonSx`（12 段样式）+ `mergeAttrs` + 按钮行为（波纹、延迟加载、不可用）       |
| `lite`   | 只走引擎的样式路径：同样的片段与配方交给 `css.attrs`，没有组件库的属性合并与行为                                               |
| `native` | 原生 CSS：同样的规则（由引擎对同样的片段算出再改成固定类）按 `@layer nb.base, nb.variant, nb.size, nb.custom` 排层，使用方的类不分层、盖过全部；组件里写类数组 |
| `bare`   | 不挂样式：Vue 本身的下限                                                                                                       |

`native` 就是"原生 CSS 也能层层覆盖"的标准做法：组件库的样式放在层里，后一层不论特异性都盖过前一层，使用方不分层的 CSS 盖过整个组件库。

场景：冷挂载（第一次见到这些组合）、重渲染（只改文字）、换档位（每个按钮的样式错开一位）、换主题、热挂载（卸载后再挂）、
定制挂载（`Provider styles` 改 `letterSpacing`、`paddingInline`，每个按钮再加 12 种 `sx` 之一，与组合同周期，新增约 108 个组合类）、
定制重渲染、组合爆炸（`sx` 与组合错开周期，约 1300 个组合类）。

| 换主题         | 216               | 197               | 212               | 18                |
| 热挂载         | 184 (147 + 42)    | 132 (67 + 62)     | 102 (53 + 49)     | 69                |
| 定制挂载       | 240 (170 + 64)    | 168 (90 + 75)     | 132 (60 + 68)     | 76                |

| 样式表（最后） | 4239 条 / 1.95 MB | 4239 条 / 1.95 MB | 134 条 / 10 KB    | —                 |

- `lite` 对 `native`：冷挂载、重渲染、换主题持平；换档位快 14%（一个类，样式重算少）；热挂载、定制挂载慢 20–30 ms
  （定制挂载要新建约 108 个组合类；热挂载的差别有一半在 layout，单轮离散很大，可能是噪声）。
- 组合爆炸：`lite` 的脚本多 198 ms（新建组合类），layout 多 20 ms（样式表大了 200 倍，插入规则后要重建规则集）。
- `real` 对 `lite`：重渲染 +36 ms（18 µs / 按钮），冷挂载脚本 +156 ms（78 µs / 按钮），内存 +15.5 MB（7.8 KB / 按钮）。

## 4. 差距从哪来（CPU 剖析，不压缩的构建，`--profile=`）

**新组合类**（`lite` 组合爆炸，约 1300 个，合计约 226 ms）：

| 函数                               | 自身耗时 | 说明                                                             |
| ---------------------------------- | -------- | ---------------------------------------------------------------- |
| `insertRule`（浏览器）             | 81 ms    | 解析规则文本：组合类把同样的声明抄进每个组合，字节越多越慢       |
| `getPriority`                      | 54 ms    | 排序比较里每次比较都重新算（正则拆伪类、查三张表）               |
| `serialize` 的两个排序比较器       | 33 ms    | 条件链每次比较都 `split` 再逐段查优先级                          |
| `composite` / `insert` / `serialize` / `merge` / `hash` | 59 ms | 合并声明表、拼规则文本、算哈希                     |

**组件库层**（`real` 重渲染 5 次 × 2000 个按钮）：

| 函数                                         | 自身耗时 | 说明                                                                       |
| -------------------------------------------- | -------- | -------------------------------------------------------------------------- |
| `mergeProps`                                 | 72 ms    | 三层展开、逐键合并 sx / class / style / ref / 事件（每个按钮两次：根、内容） |
| `hasKeys` + `restProps` 的 `ownKeys`          | 48 ms    | 对 `...rest` 的 Proxy 做 `for…in` 判空：两层陷阱，约 600 ns / 次           |
| Vue 的响应式 `get`、`withChildren` 的 `get`   | 33 ms    | 读 props                                                                   |
| 配方 `resolve`                               | 15 ms    | 每次渲染拼档位键、查表（约 1.5 µs / 次）                                    |
| `elementProps` / `css.attrs` 的收集 / `compose` | 20 ms | 再复制一遍属性；12 段样式逐层查组合缓存                                    |

挂载时另有每个按钮的 `watch`（`useDelayedLoading`）、`computed`（`useDefaults`）、4 次 `inject`、3 个事件监听（`onClick` 与波纹的两个），
这些是组件行为，不属于样式合并。

## 5. 原型（工作树 `exp/style-merge-opt`）

都是内部实现，不改样式写法与合并语义；tsx 全部 225 个测试、ui 相关目录 629 个测试通过（含新加的两条）。

| 改动                                                                                                       | 位置                                          |
| ---------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| `getPriority` 记忆化（键是源码里写过的属性名、伪类、@ 规则，数量有限）                                      | `tsx/src/styles/priority.ts`                  |
| `serialize` 排序前算好条件链权重与属性优先级，比较器里只比数字                                             | `tsx/src/styles/declarations.ts`              |
| `ownProps(rest)`：编译器生成的 `...rest` 交出背后的 attrs 普通对象（有内容时加上 children），没有键时 `undefined` | `tsx/src/runtime/component.ts`（主入口导出） |
| `mergeProps` 用 `ownProps` 判空并展开，不再对 Proxy 做 `for…in` 与展开                                       | `ui/src/utils/props.ts`                       |
| `useRecipe` 按实例记住上一次的档位与定制层，没变时不进配方拼键查表                                           | `ui/src/config/styles.ts`                     |

CPU 剖析对比（同一场景，两份不压缩的构建交错跑，取被改动的那几个函数的自身耗时之和；墙钟时间的离散太大，见下）：

| 场景                             | 基线                                                            | 原型                                   | 变化     |
| -------------------------------- | --------------------------------------------------------------- | -------------------------------------- | -------- |
| Button 重渲染（5 次 × 2000）     | 155 ms（`mergeProps` 70、判空与 Proxy 陷阱 60、`resolve` 12、`elementProps` 13） | 34 ms（`mergeProps` 14、`ownProps` 11、`elementProps` 9） | **−78%**，约 12 µs / 按钮 / 次 |

## 6. 原生 `@layer` 能不能表达引擎的合并语义

能表达主体，不能表达两处细节：

| 后面的片段写法                                        | 引擎（合成一个类）                      | 原生（后一层 `@layer`）                      | 一致 |
| ----------------------------------------------------- | --------------------------------------- | -------------------------------------------- | ---- |
| 普通值 `color: 'red'`                                 | 整体替换，含前面的 `:hover` 等条件值    | 后一层赢、与特异性无关，各状态都是 red       | 是   |
| `{ default: null, ':hover': X }`                      | 只改悬停                                | 后一层只有 `:hover` 规则                     | 是   |
| `{ default: X, ':hover': Y }`，前面写过 `':focus': Z` | 逐条件合并，聚焦时仍是 Z                | 后一层的默认值盖过前一层的 `:focus`，是 X    | 否   |
| 前面写简写 `outline`，后面写长属性 `outlineColor`     | 同一块里按属性优先级排，条件块里的简写赢 | 后一层的长属性连 `:focus-visible` 一起改掉   | 否   |
| 顶层 `null`（去掉属性）                               | 去掉                                    | 只能写 `revert-layer` / `unset`，语义不同    | 部分 |

所以"整体换成原生层叠"或"按层拆类"都要逐处核对外观（`pnpm docs:shot` + `scripts/docs/shots-compare.mjs` 逐像素比）。

## 7. 页面里的样式表（`apps/docs/dist` 预渲染的 145 页，`<style data-vue-tsx-pro>`）

- 中位数一页 54.5 KB（gzip 6.8 KB），132 个组合类；同一条声明（含条件）平均被抄 3.2 次，最重的 `data-table` 4.8 次。
- 全站合起来 1597 个组合类、656 KB（gzip 60 KB），声明重复 10 倍；换成原生 CSS 约 2000 条不重复的声明。
- 服务端渲染每页都内联这张表、不能跨页缓存，但 gzip 后不大；客户端解析 54 KB 的 CSS 约 1 ms。不是瓶颈，是组合数相乘时的风险。

## 8. 建议（按收益与风险）

1. **合入 §5 的原型**（内部实现，不改 API，测试已过）。
2. **组件库层继续压每次渲染的分配**（收益最大的方向，仍是内部实现）：
   - `buttonSx` 这类每次渲染新建的样式数组按档位与状态记住，`compileSx` 对数组也按对象缓存，命中时跳过 `css.attrs`；
   - `mergeProps` 的 sx / class / style 只有一层时不包数组（缓存才能命中）；`mergeAttrs` 一遍合出元素属性，不再经 `elementProps` 复制第二遍；
   - 挂载开销：`useDelayedLoading` 的 `watch` 等到第一次 `loading` 才建；按钮行为的回调在 setup 里建一次。
   每做一项用 `--against` 对比，`DataTable`、`Select` 的选项这类一屏几百个部件的地方受益最大（虚拟滚动每帧 16 ms 的预算）。
3. **定制层不与组件样式相乘**（结构性，要拍板）：一个元素出两个组合类——组件段（配方的基础、档位、组合档位）与覆盖段
   （`createUi` / `Provider` 的 styles、使用方的 sx，只含它改到的属性，并把组件段里同属性的条件值一起带上，保持逐条件合并的语义），
   覆盖段排在后面（`@layer` 或重复类名提特异性）。组合数从"组件组合 × 覆盖组合"降到"相加"，explode 那类场景的规则数、插入与样式重算随之下降。
   代价：一个元素两个类；简写与长属性跨段时的结果要逐处核对（§6）；小程序把组合类展开成行内样式（`styles/inline.ts`），两段要按同样的顺序合并。
   现在典型页面一百多个组合类、gzip 后几 KB，**不急**；等定制层真被大量使用、或页面的组合类数明显上涨时再做。
   可以先在 `docs:review` 里报每页的组合类数与样式表字节，当作预算盯着。
4. **可选：引擎的规则放进 `@layer`**：宿主不分层的 CSS（含 `[data-scope][data-part]` 选择器）不论特异性都能盖过组件库，
   现在 `@media` 条件块里的 `.x.x` 要更高的特异性才盖得过。这改变宿主覆盖的契约；小程序的 app 样式表只收 `:root` 与 `@keyframes`
   （`packages/mini/src/build/styles.ts`），包进层之后要先剥掉。要另议。
5. **不做**：整体换成原生 CSS（热路径没有收益，丢掉类型检查、token 短写、按需插入、绑定不重渲染、样式热更新与配方的定制层）；
   换回原子类（原型实测更新慢一倍、规则更多，§9.1）。
