# 0010 通知、广播、代理与监控

第 7 批（ROADMAP 26.7）：流程推进时谁该知道、多实例部署时页面怎么实时刷新、休假时待办交给谁、管理员看什么。

## 1. 通知：站内信箱兼发件箱

- 一张表 `flow_notification`：`readAt` 是收件人读过（站内信箱），`sentAt` 是外部投递送到了（发件箱）。
  在推进的同一个事务里写入——提交了才有通知，回滚了就没有，不会发出一条单子里并不存在的消息（发件箱模式）。
- 按这一步的流转记录生成（`runtime/notifications.ts`）：

  | 事件                   | 来自                                | 发给                             |
  | ---------------------- | ----------------------------------- | -------------------------------- |
  | `arrived` / `returned` | 新建的待办（退回来的是 `returned`） | 处理人；收件箱里的发给能认领的人 |
  | `reminded`             | 手动催办、收件箱很久没人认领        | 同上                             |
  | `dueSoon`              | 到期前的提醒                        | 同上                             |
  | `overdue`              | 待办超时                            | 同上                             |
  | `cc`                   | 抄送                                | 抄送的人                         |
  | `finished`             | 实例结束（完成、终止、撤回）        | 发起人                           |

  流程级、节点级的 `notify`（模型包早就有的设置）：`false` 不发；`to` 加收件人（同处理人的写法）；`template` 换文字。
  不发给引起这件事的人自己。

- 引擎只存事件、当时的标题与环节名、谁引起的；文案由界面按事件拼（语言包），配了模板时 `message` 是渲染好的文字。
- 外部投递：引擎选项 `notifications.deliver`。提交后逐条送；抛错的记下原因留着，`jobs.runDue` 顺带再试，最多 5 次。
  多实例部署时先带条件地占用（次数加一）再投递，同一条不会被两个进程各送一次。
- 接口：`engine.notifications.list / unread / read`，客户端同名；页面顶栏的铃铛按它列出、点一条去那张单。

## 2. 广播：PG 的 NOTIFY

- 多实例部署时，一个进程推进了，别的进程的页面也要刷新；组织目录是进程内的快照，别的进程改了也要刷新。
  用 PostgreSQL 自带的 `NOTIFY` / `LISTEN`，不引入消息队列：引擎已经只支持 PG（0008），广播随事务提交发出、回滚就不发，
  和数据一致；漏了（连接断开）也只是页面晚一点刷新，下次数据变化或重新进入页面就对了，不需要可靠投递。
- 频道（`core/channels.ts`，从包入口导出）：
  - `FLOW_CHANNEL`（`flow_changed`）：推进（负载 `{"instance": 12}`）、发布与启停（`{"process": "leave"}`）。
    作业也是推进，所以不再需要“`runDue` 返回做了几件、宿主据此通知”。
  - `ORG_CHANNEL`（`flow_org_changed`）：组织目录的 `sync`、`save*`、`removeDepartment`。
- 宿主收听：`easy-query-ts-pg` 的 `listen(pool, channel, handler)`（占一条专用连接；断了要重新 listen），PGlite 用 `easy-query-ts-pg/pglite` 的 `listen`。
  流程中心的 Worker 收听 `FLOW_CHANNEL` 后通知页面；页面把同一次改动的两下（端点自己的通知与广播）合成一次刷新。
- 负载只是提示，不带数据：收到后按自己的权限重新查询，广播不会把别人的单子内容推给不该看的人。

## 3. 代理：不在的时候交给别人

- 和待办上的“委托”（operations.ts，一份待办委托出去、办完交回）不同，代理是长期规则：某人不在（休假、出差）的这段时间、
  这些流程，**新到他手上**的待办直接交给代理人。参考常见 OA 的“流程代理”，不做“代理人替本人处理已有待办”——已经在手上的要交出去用转办，
  一份待办只有一个处理人，权限、通知、统计都不用区分“本人还是代理人在办”。
- 表 `flow_proxy`：委托人、代理人、流程（空是全部）、开始、结束（空是一直到撤销）、说明、谁设的、撤销时刻。
  只能设自己的，管理员可以替别人设；不能代理给自己，结束要晚于开始。
- 解析在 `Execution.insertItem`——新建待办只有这一个口子，发起、流转、退回、转办、委托、加签、会签都经过它：
  - 直接落到人的：交给代理人，`proxyFor` 记本该是谁的（待办列表写“代某某”，到达通知发给代理人）。
  - 代理人自己也设了代理：顺着找下去；绕回来时停在绕回之前的那个人。
  - 收件箱：候选里的人设了代理时，代理人也加进候选（本人回来了照样能认领）；角色、部门的候选不展开。
  - 会签：代理人本来就在这一组时不代理，免得一人两票。
- 接口：`engine.proxies.list / save / cancel`，客户端同名；流程中心的“代理”页设、撤销、看别人交给我的。

## 4. 监控与统计

- `engine.stats.overview({ from, to, processKey, timeZone })`（端点只给管理员）：这段时间（默认 30 天）发起、结束、没走完的，
  现在进行中的、开着的待办与其中超时的、失败的作业；各流程平均走多久；各环节平均停留与超时（慢的在前，就是瓶颈）；
  谁手上压着待办；按天的发起与结束（按调用方的时区分日子）。
- 计数用分组查询在库里算（`groupBy`、`count(条件)`）；时长要两列相减，按这段时间结束的行在引擎里算——
  范围有界（看板按天、按月看），不为它引入各库不同的日期函数。数据量大到这一步慢时，再换成定时汇总的统计表。
- 流程中心的“监控”页：指标、每天的趋势、各流程、最慢的环节、谁压着待办；数据变了跟着刷新。
- 顺带修了线路：端点读参数时也把时刻还原成 Date（与客户端读结果同一个 reader，`client/protocol.ts` 的 `readWire`），
  之前参数里的 Date 到引擎不是 Date，查询只能自己 `new Date(...)` 兜着。
